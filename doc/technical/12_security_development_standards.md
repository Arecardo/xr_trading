# 安全开发规范

本文档适用于 XR-Trading 全部代码、文档、测试数据、脚本、CI artifact 和 Git 历史。核心原则是：仓库只保存代码与无敏感性的配置结构，环境身份和网络拓扑只在运行时由受控平台注入。

## 1. 禁止进入仓库的信息

- 真实 API Key、App Key、Access Token、Bearer Token、密码、Cookie、签名、助记词、私钥、证书私钥和数据库连接凭据。
- 生产、测试或个人环境的非回环 IP、主机名、端口组合、VPN/跳板机地址、内网域名、云资源 ID 和可推导网络拓扑的信息。
- `.env`、credential 文件、密钥库、数据库文件、备份、日志、抓包、原始 Provider 响应、覆盖率文件和本地运行数据。
- 包含真实账户、订单、持仓、资金、客户或个人身份信息的 fixture、截图、SQL、日志和错误上下文。
- 可以直接访问环境的 URL，即使它当前已失效；失效凭据仍必须按泄漏处理。

`127.0.0.1`、`localhost`、`::1`、Docker Compose 中的通用服务名以及明显的 `example`/`local-only` 占位值可用于本地测试和文档。它们不代表任何可访问环境。Provider 官方公开域名和官方文档链接可以保留，但认证信息必须单独注入。

## 2. 配置与网络规则

- 代码只读取环境变量或 Secret Manager 引用，不硬编码环境地址、端口和凭据。
- `.env.example` 只描述变量名和不可用的本地占位值；真实 `.env` 必须被 `.gitignore` 排除。
- 本地容器发布端口必须显式绑定 `127.0.0.1`。测试使用随机端口；生产端口由部署平台和网络策略管理，不写入仓库。
- 默认配置必须 fail closed：关键凭据缺失时启动失败，不得回退到可预测的生产可用密码或 Token。
- 日志、指标、错误 envelope 和审计上下文不得输出连接串、认证头、签名、Provider 原始响应或 secret 环境变量值。
- 测试只使用短、明显、不可用的占位值；不得复制生产响应后再手工删字段。

## 3. 开发与评审流程

1. 开发前确认新配置属于代码结构还是环境秘密；后者只能进入本地未跟踪文件或部署平台。
2. 提交前执行 `make security-check`，并检查 `git diff --cached` 和待提交文件列表。
3. Pull Request 必须说明新增的网络访问、凭据类型、权限范围、日志脱敏和失败策略。
4. 对 `.gitignore`、CI、部署、Adapter、认证、日志或网络监听的修改必须进行安全评审。
5. 不得用宽泛 allowlist、关闭规则或 `gitleaks:allow` 绕过门禁。确有误报时，例外必须限定到单一 finding，记录原因、负责人和到期时间。

## 4. 自动安全门禁

GitHub Actions 的 `Security preflight` 是所有编译和测试 job 的前置依赖：

- 自定义仓库策略扫描：拒绝敏感文件、非回环 IP、外部 `host:port`、URL 内嵌凭据、非本机容器端口映射和私钥材料。
- Gitleaks 固定版本全历史扫描：检测当前文件和历史提交中的密码、API Key、Token 及高熵凭据，并在日志中完全脱敏。
- 扫描器自身运行单元测试；工具二进制从官方 release 下载并校验 SHA-256。
- 安全预检失败时，格式、单测、race、PostgreSQL 集成和构建全部不启动。

本地执行：

```bash
brew install gitleaks
# 在仓库根目录执行
make security-check
```

CI 不上传包含 finding 原文的报告，避免将疑似 secret 复制到 artifact 或日志。

## 5. 泄漏响应

发现疑似泄漏后立即停止发布，不要只删除文件或增加 allowlist：

1. 撤销或轮换凭据、证书和 Token，收紧相关权限并检查访问记录。
2. 隔离受影响环境，确认是否存在异常请求、资金操作或数据读取。
3. 确定泄漏首次出现的 commit、传播范围和 artifact/cache/log 副本。
4. 必要时重写 Git 历史并重新克隆，但历史清理不能替代凭据轮换。
5. 记录事件、根因、影响、处置和防复发门禁；涉及资损风险时升级为安全事件。

任何人都不应在 Issue、PR 评论、聊天或日志中粘贴疑似 secret 的完整值；只保留类型、来源和脱敏后的首尾字符。
