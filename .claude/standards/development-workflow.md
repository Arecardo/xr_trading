# 开发工作流规范：文档驱动 + 多 Agent 协作

> 适用范围：整个仓库。将 `market-info-service` 实施计划中已验证的协作模式沉淀为仓库级流程。
> 规范状态：第一版。
> 最近更新：2026-08-04

## 1. 核心模式

XR-Trading 采用 **文档驱动（spec-first）+ 多 Agent 分波协作** 的开发模式：先把设计写进 `doc/`，冻结共享契约，再由多个执行 Agent 并行实现纵向切片，由整合负责人统一合并。此模式已在行情服务 M0–M4 验证有效，全仓库沿用。

## 2. 标准开发循环（每个任务）

1. **读设计**：读 `doc/` 对应模块文档与本规范集；设计缺失或过时，先补/改设计文档。
2. **定契约**：确认涉及的共享 DTO、接口、错误码、migration 顺序、API 契约是否已冻结；未冻结的先由整合负责人冻结。
3. **写测试 + 实现**：优先表驱动测试，覆盖正常/边界/失败路径；非确定性能力（时间、UUID、网络、DB、Provider）通过接口注入。
4. **过门禁**：运行对应语言的提交前门禁 + `make security-check`。
5. **同步文档**：API/migration/配置变化时同步更新设计文档与示例。
6. **报告**：说明改动文件、验证命令、风险、遗留未决项。

## 3. 任务状态机

任务状态统一使用：

- `TODO`：未开始。
- `READY`：依赖已满足，可领取。
- `IN_PROGRESS`：正在实现，必须有唯一负责人。
- `BLOCKED`：存在明确阻塞条件，需记录原因。
- `DONE`：产出、测试、完成条件三者全部满足。

覆盖率达标**不能**替代业务边界、并发和事务测试。任一任务只有同时满足「输出 + 测试 + 完成条件」才可标记 `DONE`。

## 4. 里程碑与并行波次

- 大型模块拆分为里程碑（M0、M1…），每个里程碑有明确「退出条件」。
- 同一波次内只并行**确实独立**的任务；共享接口、migration、`go.mod/go.sum`、路由注册、Compose、CI 文件由**整合负责人统一修改**。
- 依赖关系用 mermaid flowchart 在实施计划中显式画出。
- 参考模板：`doc/technical/market_information_service/implementation_plan/`。

## 5. 多 Agent 协作规则

- 同时最多 **3 个执行 Agent + 1 个整合 Agent**；只有确实独立的任务才并行。
- **每个目录设唯一写入者**；子 Agent 不修改共享接口和统一装配文件。
- 子任务限定为**一个纵向切片**或 1–2 个文档章节，避免重复读取整套设计文档。
- 子 Agent **不提交 Git、不格式化无关文件**；完成时报告变更文件、验证命令、风险和未决项。
- 共享 DTO、Repository 接口、错误码、migration 顺序**先冻结再并行实现**。

## 6. 优先级原则（当前阶段特别强调）

- **先纵切后深化**：优先打通最小端到端闭环（walking skeleton），再深化任一模块。
- **按价值/风险排序，而非按难易**：策略、风控、组合构建、回测、执行是差异化核心，优先于继续打磨已「够用」的行情服务。
- **回测优先于实盘**：回测是零资金风险验证策略+风控逻辑的最便宜手段，且须复用同一套策略/风控代码。
- **真金白银路径最严谨**：把最高的测试与对账严谨度投入到风控/执行/对账链路。

## 7. 完成定义（Definition of Done）

一项工作可标记完成，当且仅当：

- 设计文档与实现一致且已同步更新。
- 单元/集成测试通过，达到对应语言的质量门禁。
- 安全门禁通过，无凭据/敏感数据泄漏。
- 若属核心交易链路，具备可复现性与对账能力。
- 报告了遗留未决项与后续任务。
